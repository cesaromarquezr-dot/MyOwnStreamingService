# Universal franchise, saga, relationship, and connected-page architecture

This extension amplifies the existing 500 canonical capabilities. It does not add a second franchise system or a second navigation system.

## 1. Franchise and saga identity

A franchise/saga is an organizational identity above canonical works. Examples include the MCU, Spider-Verse, Twilight Saga, Wizarding World/Harry Potter, Fantastic Beasts, Fast & Furious, and a historical continuity such as the 2013–2023 DCEU. The system stores the franchise identity and membership separately from individual works.

A work can belong to more than one useful grouping, and membership does not automatically mean identical continuity.

## 2. Relationship graph

The universal graph supports explicit relationship types:

- same continuity
- sequel / prequel
- spin-off
- crossover
- cameo / appearance
- alternate universe
- character variant
- reference / meta-reference
- adaptation / remake / reboot
- visual or character-design influence
- shared actor / creator / location
- soundtrack connection
- leads into
- related

`continuity_effect` is stored separately from `relationship_type`. A reference can therefore be highly relevant while having `continuity_effect = none`. A cameo can connect two works without asserting that the originating series shares the receiving work's normal continuity.

This prevents false binary decisions such as `connected` vs `not connected`.

## 3. Timeline views

One timeline infrastructure produces multiple views:

- release order
- chronological/story order
- franchise order
- branch/continuity order
- character appearance order
- actor/creator career order
- reference timeline
- influence timeline
- media-version timeline
- scene/X-Ray timeline

The graph supplies the relationships; the timeline supplies temporal ordering. A user collection can independently choose its own presentation order.

## 4. Connected page contract

Every major page should be able to expose a common context rail/section using the canonical IDs available for its current entity. Typical connections include:

`Franchise → Timeline → Versions → People → Characters → Related Media → X-Ray → Likes → Collections/Playlists → Recommendations → Reviews → Chat/Share → Stories → Group Watch → Shop/Merchandise → Releases → Availability`

The page does not own those features. It links to the canonical owner. This makes improvements to one capability appear consistently across Home, Movies, TV, Music, Details, Player, X-Ray, Collections, Search, Stories, My TV, Marketplace, Storefronts, Live Shopping, and profiles.

## 5. TV Intro Library

TV Shows receives a dedicated `TV Intros` section. It shows opening sequences indexed from the user's accessible TV library.

An intro is not a standalone media file in application storage. It references:

- series canonical work
- exact media version
- start offset
- end offset
- optional season/episode context
- detection source and confidence

The home server remains the owner of media bytes. The backend returns safe identifiers and playback metadata, never a private filesystem path. Intro detection may be manual, imported from a trusted catalog, or generated by a home-server media analysis job.

The same intro metadata can later power skip-intro, intro replay, intro history, X-Ray scene context, and My TV programming without creating separate intro systems.

## 6. External ratings

Ratings are provider-specific records. The platform must never silently average IMDb, Rotten Tomatoes, TMDB, Metacritic, or other providers into one unexplained score.

The backend now supports provider adapters and backend-only credentials. The current adapter strategy can use:

- TMDB API for TMDB community ratings
- OMDb where licensed/configured fields expose IMDb, Rotten Tomatoes, and Metacritic values
- direct licensed provider integrations in the future

IMDb offers licensed metadata and ratings products through its developer/licensing program. TMDB documents application authentication and API usage and requires attribution/licensing appropriate to the project. OMDb is a third-party service and has its own key and usage/license terms. Provider availability and commercial rights must be verified before production distribution.

Each returned rating retains provider, kind, value, scale, vote/review count when supplied, source URL when supplied, and freshness. Personal profile ratings remain a separate domain.
